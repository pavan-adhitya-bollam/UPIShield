1 Identification of Selected Production Model

Through static inspection of the codebase, model artifacts, and active configuration files, the following production specifications were verified:

  • Algorithm: Histogram-based Gradient Boosting Classification (HistGradientBoostingClassifier from sklearn.ensemble). Bins continuous numeric features into integer bins (max_bins=255), building gradient boosted trees (max_depth=6, max_iter=200, learning_rate=0.1).
  • Active Model Artifact: Loaded from models/best_histgradientboosting_model.joblib (212,344 bytes) via joblib.load() in ml_service/model_loader.py.
  • Model Version Tag: Explicitly configured as "HistGradientBoosting v1.0" in ml_service/config.py.
  • Production Execution: The application uses the real trained model when the FastAPI microservice is running. Node.js backend connects to FastAPI at http://localhost:8000/predict via PredictionProvider.js. If FastAPI is offline, Node.js transparently falls back to MockPredictionProvider.js as a safety failover.

2 Why This Model Was Selected (Technical Justification)

Model selection was conducted based on banking operational constraints rather than naive accuracy:

  • Primary Metric — PR-AUC (0.3851): With an imbalanced 5% fraud rate, ROC-AUC is misleading because abundant true negatives keep the False Positive Rate artificially low. PR-AUC measures true fraud detection capability without distortion from non-fraud volume. HistGradientBoosting scored the highest PR-AUC of all candidates.
  • Probability Calibration — Brier Score (0.0362): The system translates predicted probabilities directly into an end-user risk score (Risk Score = round(P * 100)). HistGradientBoosting produced the lowest Brier score (0.0362 vs. XGBoost's 0.0838, CatBoost's 0.1040), proving that its probability estimates reflect real risk probabilities.
  • Minimizing False Alarms (False Positives = 786):** In consumer UPI payments, false positives block innocent customers from paying for food, hospital bills, or travel. HistGradientBoosting produced only 786 false alarms out of 19,000 legitimate payments (FPR = 4.14%), substantially outperforming other default baseline trees.
  • Real-World Trade-Off: HistGradientBoosting strikes a deliberate balance: 57.6% of frauds detected while keeping genuine user blocking down to 4.14%. Logistic Regression detected more frauds (Recall 68.3%), but generated an intolerable 1,675 false alarms.
  • Objective Position: The model is not universally superior in all metrics: CatBoost achieved a slightly higher F1 (0.4929 vs. 0.4877) at threshold 0.85, and Random Forest had slightly higher ROC-AUC (0.8746 vs. 0.8716). HistGradientBoosting was chosen as the most balanced fit for UPI payments given the PR-AUC, precision, and calibration priorities.

4 Accuracy & Real-World Performance Explained

  • Accuracy (93.95%): Ratio of total correct predictions (18,790) to total transactions (20,000).
  • The Accuracy Paradox: A completely useless model that labels 100% of transactions as "Genuine" achieves 95.0% accuracy simply because 95% of transactions are genuine. Therefore, accuracy alone is never acceptable evidence for fraud detection defense.
  • Precision (42.29%): Out of every 100 fraud alerts raised by our system, 42.3 are confirmed frauds and 57.7 are false alarms.
  • Recall (57.60%): Out of every 100 actual fraud attempts passing through UPI, our system intercepts 57.6 and misses 42.4.
  • F1-Score (0.4877): Harmonic mean ($2 \cdot rac{P \cdot R}{P + R}$) summarizing precision-recall balance.
  • PR-AUC (0.3851): Area under the Precision-Recall curve. Random guessing baseline is only $0.05$ (the dataset fraud prevalence). Our model achieves a 7.7× lift over random guessing.
  • Test Set vs. Production Reality: Test results come from a static, synthetic test split. Real-world fraud patterns exhibit concept drift (evolving QR frauds, social engineering), requiring continuous retraining and adaptive thresholds.

5 Dataset, Features & Preprocessing Pipeline

Dataset Structure:
  • Source: upi_fraud_dataset_behavioral_v2.csv
  • 100,000 transactions, 35 raw columns
  • 95,000 Genuine (95%), 5,000 Fraud (5%)
  • Simulated behavioral UPI transaction distribution
Split & Feature Configuration:
  • Split: 60% Train, 20% Val, 20% Test (Stratified)
  • Random Seed: random_state = 42
  • Final Feature Count: 76 features
  • Leakage Prevention: fraud_type explicitly dropped
  • Explicitly Excluded Columns (7): transaction_id, customer_id, sender_upi, receiver_upi, device_id, ip_address, and fraud_type. Excluding fraud_type prevents direct target leakage.
  • Numerical Features (13): Amount, account ages, beneficiary frequency, 10-minute/1-hour/24-hour transaction velocities, balances, behavioral deviation. Missing values imputed with median.
  • Datetime Features (5): Day of week, day, month, year, hour extracted from timestamps.
  • Categorical Features (12 → 58 one-hot columns): Transaction type, merchant categories, device/location changes, OS, app name, money flow patterns. Missing categories imputed with 'NONE' or 'P2P'.

6 Risk Score Calculation & Application Integration

How machine learning probabilities become user-facing risk indicators in the MERN payment flow:

Exact Mathematical Formula:

probability = model.predict_proba(features)[:, 1][0]
riskScore = int(round(probability * 100))   /* Range: 0 to 100 */

  • Risk Tier Boundaries:
    • LOW (0 – 29): Normal payment behavior → Allowed directly.
    • MEDIUM (30 – 59): Moderate deviation → OTP Verification & Allow.
    • HIGH (60 – 79): High risk anomaly → Secondary authentication / Warning.
    • CRITICAL (80 – 100): Extreme risk → Transaction Blocked, Manual Review.
  • Nature of Displayed Metric: The UI displays a model-derived risk estimate, NOT an absolute guarantee of fraud.
  • Payment Flow Timing: When the user submits the payment form on /send-money, the system executes an assessment API call to FastAPI before MPIN authorization. The user is redirected to /fraud-result where the Risk Gauge and safety recommendations are displayed alongside MPIN confirmation.

8 Professor Viva Defense: 10 Essential Questions & Answers

Q1: Which machine learning model did you select for production?
"We selected the HistGradientBoosting Classifier (version 1.0) implemented in scikit-learn. It is serialized as best_histgradientboosting_model.joblib and served in real time by our FastAPI microservice."
Q2: Why did you select HistGradientBoosting over XGBoost and Random Forest?
"Because it achieved the highest PR-AUC of 0.3851 and the lowest Brier score of 0.0362. In imbalanced fraud detection, PR-AUC and probability calibration are far more critical than raw accuracy or uncalibrated ROC-AUC. It also produced the fewest false positives among boosting models."
Q3: Exactly how many models did you compare?
"We successfully benchmarked 7 models: Logistic Regression, Random Forest, Extra Trees, HistGradientBoosting, XGBoost, LightGBM, and CatBoost. An eighth candidate, TabPFN, was attempted but excluded due to environment compatibility constraints."
Q4: What is your model's accuracy, and why is accuracy not enough?
"Our test accuracy is 93.95% (reported as ~94% on our landing page). However, accuracy is misleading because fraud accounts for only 5% of the data. A naive model that classifies every transaction as legitimate would achieve 95% accuracy while catching zero fraud."
Q5: What is the difference between Precision and Recall in your project?
"Precision (42.29%) measures how many flagged transactions were truly fraudulent, directly governing customer friction. Recall (57.60%) measures what percentage of all incoming fraud attempts were caught, directly governing direct financial loss."
Q6: What is PR-AUC and why is it superior to ROC-AUC here?
"ROC-AUC includes True Negatives, which artificially inflates the curve when the negative class is massive. PR-AUC evaluates only the positive minority class (fraud). For our 5% fraud rate, random guessing yields a PR-AUC of 0.05; our score of 0.3851 represents a 7.7x lift."
Q7: What does the Brier Score indicate in your evaluation?
"The Brier score measures the mean squared difference between predicted probabilities and actual binary outcomes (0 is perfect calibration). HistGradientBoosting achieved 0.0362, ensuring our 0–100 risk score reflects genuine statistical probability."
Q8: How do you calculate the transaction risk score?
"The model computes the fraud probability via predict_proba(), which is converted via Risk Score = int(round(probability * 100)). Scores are grouped into Low (<30), Medium (30–59), High (60–79), and Critical (≥80)."
Q9: How do you balance false alarms against missed fraud?
"Rather than blocking all suspicious transactions, we enforce tiered risk responses: Medium and High risk trigger secondary authentication (MPIN/OTP challenge), whereas only Critical risk (≥80) blocks the transaction outright. This minimizes genuine user drop-offs."
Q10: How do you verify the deployed model is actually being used at runtime?
"The Node.js backend sends an HTTP request to FastAPI's /predict endpoint. FastAPI loads best_histgradientboosting_model.joblib into memory and validates input against the 76 features in feature_names_in_, returning model version metadata displayed on the React frontend."
